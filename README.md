## 一句话

把每月工资在**到账那一刻**切成「刚性 / 缓冲 / 灵活」三池，用发薪日现金流预测提前标出哪几天会紧绷；用户每次动用锁定资金，这个动作本身成为校准模型的信号。

**不需要跨行数据，也不上传任何信息。**

---

## 为什么做这个

青年群体的财务困境通常被描述成「不会记账」，但真正的问题发生在两个时点：

1. **发薪日**——钱一次性到账，没有分配机制，于是按花销顺序被动消耗；
2. **月中某几天**——固定支出集中扣款，账户余额触底，只能临时周转或透支。

记账类产品解决的是「事后知道钱花哪了」，这两个时点它都管不到。而银行侧建模的常规路径是拿跨行流水做全量画像，这在青年客群上恰恰是最难获得的数据。

本方案的取舍是：**放弃全量画像，只做发薪日这一个锚点**，把数据缺口转化为可从行为中推断的信号。

---

## 核心机制

### 1. 三池分账：以发薪日为锚点

工资到账即刻按历史刚性支出切分：

| 池 | 用途 | 可动性 |
|---|---|---|
| 刚性池 | 房租、车贷、保费、通勤等确定支出 | 锁定 |
| 缓冲池 | 应急备用 | 半锁（需主动解冻） |
| 灵活池 | 日常消费 | 自由 |

锚点是发薪日而非自然月——因为现金流的真实周期由收入决定，不由日历决定。

### 2. 解冻即校准（本方案的核心）

**用户动用锁定资金，等于用行动承认「预测太紧了」。**

这是一条免费、实时、无需授权、无需问卷的标注信号。系统据此把预测的缩放系数 α 往宽松方向调整；反之若长期不需解冻，则逐步收紧。

它替代的正是「跨行数据」原本要提供的信息，因此整套方案可以在**没有外部数据授权**的前提下运转。

### 3. 三层分工

```
预测层   LightGBM 分位数回归（q10 / q50 / q90）→ 余额区间
   ↓
校准层   非对称 α 修正（上调快、下调慢）→ 贴合个体真实开销节奏
   ↓
护栏层   纯规则引擎 → 额度上限与合规拦截（明确不是 AI）
```

护栏层用规则而不是模型，是刻意的：涉及额度与合规拦截的判断必须可解释、可审计、可追责。

## 关键指标

> 以下全部为**合成数据回放**结果，不构成精度承诺。

| 指标 | 数值 | 口径 |
|---|---|---|
| 预测误差 MAPE | 33.70% → 26.02% | 4 个完整发薪周期，200 名虚拟用户 |
| 校准引入的偏差 gap | +1.79 → +0.52 个百分点 | 校准后误差 − 未校准误差，降幅 71% |
| 校准系数 α | 0.860 → 0.916 | 由行为信号驱动，单调趋向无偏值 1.0 |
| 偏紧信号占比 | 66.52% → 64.24% | 校准后预测余额低于实际期末余额的周期占比 |
| naive 基线 MAPE | 97.01% | 按上月同项支出直接外推 |

**关于 gap 的说明**：校准层的作用不是提高拟合精度，而是纠正**系统性偏差方向**。gap 全程为正、但单调收窄，说明校准在持续纠偏而非放大误差。这一点我们不回避。

## 目录结构

```

  src/gen_data.py        合成流水生成（200 用户 × 12 个月）
  src/pipeline.py        特征工程

  src/simulate.py        逐周期回放与指标统计
  src/make_dashboards.py 可视化数据导出
  params.json            唯一参数源
  results/               收敛曲线、敏感性、汇总
  docs/                  数据说明、特征定义、前端接口约定
```

## 本地运行

**前端**：直接用浏览器打开 `index.html`，无需服务器、无需安装。

**仿真**：

```bash
cd simulation
pip install -r requirements.txt
python run_all.py
```

输出写入 `results/`。数据生成使用固定随机种子，结果可复现。

## 数据与合规

- 全部数据由 `simulation/src/gen_data.py` 合成生成，**不含任何真实用户交易信息**，也不涉及任何真实金融机构数据。
- 前端页面不发起任何网络请求，计算全部在浏览器内完成；这一点可在体验页按 F12 → Network 自行验证。
- 产品设想形态为商业银行私有云本地部署，不依赖外部大模型 API。
- 参赛材料中的指标均为合成数据回放结果，正式上线前须以真实业务数据重新标定。
